# E-006: Схема конфига источника собирается из коннекторов

## Цель

Добавление коннектора не требует правки ни одного общего файла: вариант конфига источника
объявляется в директории коннектора и попадает в схему профиля кодогенерацией.

## Контекст (читать перед началом, по порядку)

1. **Дефект, ради которого эпик существует.** `profiles/schema.ts` содержит
   `SourceSchema = z.discriminatedUnion("kind", [RssSourceSchema])`. Каждый новый источник
   обязан дописать сюда свой вариант, то есть тронуть файл под меткой `profile-schema`.
   Значит два агента, добавляющих коннекторы, сериализуются — при том что всё остальное для
   параллельной работы уже сделано.
2. `packages/connectors/src/registry.ts` — как выглядит цель. Он **генерируется**
   `scripts/gen-connectors.mjs`, актуальность проверяет `pnpm verify` через `--check`, и
   именно поэтому реестра коннекторов нет в serialize-списке. Схема источника должна
   получить то же свойство.
3. `packages/core/src/connector.ts` — у коннектора **уже есть** `configSchema`. Информация,
   которую сейчас дублирует `profiles/schema.ts`, в коннекторе присутствует; задача не
   «придумать, где её взять», а перестать дублировать.
4. `apps/pipeline/src/ingest.ts` — доказательство, что остальной путь уже агностичен:
   `getConnector(source.kind)` и `config: Record<string, unknown>`. Ниже профиля вид
   источника нигде не зашит.
5. CLAUDE.md § Правила параллельной работы, пункт 5 и
   [.claude/rules/backlog.md](../../.claude/rules/backlog.md) § serialize-реестр —
   формулировка «устранённый хотспот лучше запертого». Этот эпик — её применение.

## Объём — карта файлов

- `profiles/schema.ts` — общая часть записи об источнике (`key`, `kind`, `weight`,
  `enabled`, `fixture`) и сборка союза из вкладов коннекторов.
- `scripts/gen-connectors.mjs` — генерация вкладов наряду с реестром.
- `packages/connectors/src/*/index.ts` — коннектор объявляет свой вариант.
- `packages/connectors/src/registry.ts` — генерируемый файл, руками не править.
- `packages/connectors/src/index.ts` — одна строка ре-экспорта вкладов. Правка разовая,
  не пер-коннекторная.
- `profiles/package.json`, `profiles/tsconfig.json` — ребро зависимости
  `profiles → connectors` (`workspace:*` и `references`). Цикла не создаёт: `core` и
  `connectors` о `profiles` не знают.
- `pnpm-lock.yaml` — следствие предыдущего пункта.
- `profiles/_test.ts` — если изменится форма записи источника. Цель — нулевой дифф.
- тесты рядом с затронутым кодом.

Карта расширена владельцем 2026-08-29 по итогу plan-gated стопа: первые четыре пункта были
в ней с самого начала, остальные — прямое следствие самого диффа, без них работа не делается.
Новых serialize-меток это не требует: `profiles/*` уже покрыт удерживаемой меткой `profiles`,
остальные файлы меткам не соответствуют. `vitest.config.ts` в карту НЕ входит: глоб
`profiles/**/*.test.ts` добавлен отдельно и заранее, чтобы эпику не пришлось брать метку
`toolchain` и сериализоваться с E-007.

## Вне объёма

- Новые коннекторы. Этот эпик не добавляет источников — он снимает блокировку с тех, кто их
  добавит (E-008, E-009).
- Схема профиля вне блока источников: `prefilter`, `selection`, `llm`, `delivery`.
- Загрузчик профиля и `pnpm profile:validate` — меняются только если сломались.

## Критерии приёмки

- [ ] КОГДА в `packages/connectors/src/` появляется новая директория с коннектором и
      запускается `pnpm gen:connectors`, ТО его конфиг проходит валидацию профиля **без
      единой правки в `profiles/schema.ts`**.
- [ ] КОГДА в профиле указан `kind`, которому не соответствует ни один коннектор,
      ТО ошибка называет неизвестный вид и перечисляет известные — на этапе разбора
      профиля, а не при обращении к сети.
- [ ] КОГДА в конфиге источника опечатка в имени поля (`chanel` вместо `channel`),
      ТО валидация профиля падает с указанием поля — то есть свойство, ради которого схема
      писалась на TypeScript, а не на YAML, сохранено.
- [ ] КОГДА коннектор добавлен, но `pnpm gen:connectors` не запущен,
      ТО `pnpm verify` краснеет и говорит, какую команду выполнить.
- [ ] КОГДА два коннектора объявляют один и тот же `kind`,
      ТО генерация падает с именами обеих директорий, а не выбирает одну молча.
- [ ] КОГДА ветка добавляет коннектор-пустышку и запускает `pnpm gen:connectors`,
      ТО `git diff --name-only` **относительно коммита, добавившего этот коннектор**, не
      содержит `profiles/schema.ts` — цель эпика измерена, а не заявлена. Пустышка в PR не
      остаётся.
      _Переформулировано владельцем 2026-08-29: прежний текст сравнивал с `main`, а ветка
      E-006 сама меняет `profiles/schema.ts`, поэтому критерий был неизмерим при любом исходе._

## Верификация

```bash
pnpm gen:connectors
pnpm profile:validate
pnpm verify
pnpm digest:run --profile profiles/dist/_test.js --fixtures --dry-run
```

## Границы

**Автокомплит конфига — то, ради чего схема на TypeScript.** Решение, собирающее союз через
`z.record(z.string(), z.unknown())`, формально «работает» и уничтожает единственную причину
не писать профили в YAML. Если типизацию сохранить не удаётся — это находка для владельца, а
не повод тихо ослабить схему.

**Цикла зависимостей быть не должно.** Сейчас `connectors → core`. Если `profiles → connectors`
создаёт цикл — генерировать отдельный модуль вкладов, а не тянуть пакет целиком.

**Профиль по-прежнему не импортирует ничего, кроме `profiles/schema.ts`.** Это правило про
файлы профилей; на сам `schema.ts` оно не распространяется, но проверить, что оно не поехало,
обязательно.

## План реализации

_Написан read-only Plan-агентом 2026-08-29 и одобрен владельцем до начала кода (`autonomy: plan-gated`). Числа ниже — измерения на установленных версиях, не память._

### Выбранная форма: вклад-данные в генерируемом `registry.ts`, союз собирается в `schema.ts`

Генератор дописывает в тот же `registry.ts` второй экспорт — кортеж
`{ kind: "<литерал>", config: <connector>.configSchema } as const`, **без** приведения к
`AnyConnector`. `profiles/schema.ts` держит общую часть записи (`key`/`weight`/`enabled`/
`fixture`), хелпер `sourceVariantSchema<K extends string, C>(kind, config)` и
`buildSourceSchema(contributions)` с mapped-tuple типом и одним локализованным приведением
внутри билдера.

**Почему не «генерировать готовые варианты в `profiles/source-variants.generated.ts`».** Типы
там проще — приведение не нужно вовсе. Но метка `profiles` в `scripts/epics.mjs` покрывает
префикс `profiles/`, поэтому генерируемый файл под `profiles/` вернул бы каждому
коннекторному эпику метку `profiles`: E-006 снял бы один хотспот и создал другой. Весь
пер-коннекторный дифф обязан оставаться внутри `packages/connectors/**`, где меток нет.
Брать этот вариант запасным, только если шаг 0 покажет, что mapped-tuple не типизируется.

**Почему не «строить союз в рантайме из `connectors` без кодогенерации».** `AnyConnector =
ConnectorDefinition<never, never>` стирает `TConfig`, а `kind` в контракте объявлен как
`string`. `z.literal(c.kind)` даёт `ZodLiteral<string>`, и `Source` схлопывается в
`{ kind: string; config: never }` — **без единой ошибки компиляции**. Это ровно тот отказ,
о котором предупреждает `## Границы`. Вдобавок AC #4 становится недоказуемым: если
генерировать нечего, `pnpm verify` не может покраснеть на «не запущен `gen:connectors`».

### Шаги

0. **Тип-спайк до всего остального (~20 минут).** Захардкодить в `schema.ts` кортеж
   `[{ kind: "rss", config: RssConfigSchema } as const]`, написать `buildSourceSchema` с
   mapped-tuple, прогнать `pnpm typecheck`. Проверяемое утверждение: `z.discriminatedUnion`
   в zod 4.4.3 требует `readonly [$ZodTypeDiscriminable<Disc>, ...$ZodTypeDiscriminable<Disc>[]]`,
   и mapped-тип над непустым кортежем обязан этому удовлетворить. Не удовлетворяет —
   переключиться на запасной вариант и записать причину в `## Заметки`. Спайк откатывается.
1. **`scripts/gen-connectors.mjs`: извлечение `kind` из AST.** Вынести чистую функцию
   `collectConnectors(entries)` (тестируемую без файловой системы). `kind` и имя экспорта
   доставать через `typescript` (`ts.createSourceFile`), а не регексом: регекс найдёт `kind:`
   в комментарии или во вложенном объекте. Падать явно, если в файле нет ровно одного
   `defineConnector` с литеральным `kind`, — сообщение называет директорию.
2. **Ключ реестра — объявленный `kind`, а не имя директории.** Сейчас они совпадают
   случайно, а `getConnector(source.kind)` ищет по `kind`. Это же делает AC #5
   воспроизводимым: две директории с разными именами могут объявить один `kind`.
3. **Проверка дублей в генераторе.** `kind → dirs[]`, при `length > 1` — выход с кодом 1 и
   сообщением, называющим **обе** директории. Работает и в обычном прогоне, и под `--check`.
   Полагаться на zod нельзя: карта дискриминанта строится **лениво**, при первом `parse`, и
   ошибка приходит голым `Error("Duplicate discriminator value \"rss\"")` без имён директорий,
   мимо доменных классов и мимо форматирования issues в валидаторе профилей.
4. **Второй экспорт в шаблоне генератора.** Кортеж вкладов с `as const`. Обновить текст
   staleness-сообщения: устаревание теперь возможно и от смены `kind`, не только от
   добавления/удаления директории. Строку `Run: pnpm gen:connectors` сохранить дословно — на
   неё смотрит AC #4.
5. **Перегенерировать `registry.ts`.** Руками не править.
6. **`packages/connectors/src/index.ts`** — одна строка ре-экспорта `sourceVariants`. Правка
   разовая, не пер-коннекторная.
7. **`profiles/package.json` + `profiles/tsconfig.json`** — ребро `profiles → connectors`
   (`workspace:*` и `references`), затем `pnpm install`. Цикла не создаёт: `core` и
   `connectors` о `profiles` не знают.
8. **`profiles/schema.ts`** — переписать блок источника. Экспортировать `buildSourceSchema`
   (тест должен проверять механизм на синтетических вкладах, а не на «rss»). `Source =
   z.infer<...>` — **именно `infer`, не `input`**: `configSchema` объявлен как
   `z.ZodType<TConfig>`, у zod 4 входной тип там `unknown`, и переключение на `z.input` тихо
   превратит `config` в `unknown`. Третьим аргументом `z.discriminatedUnion` передать
   `{ error }` для сообщения AC #2. Туда же — compile-time утверждение, что `Source["kind"]`
   не расширился до `string`; оно должно жить **в собираемом файле, а не в тесте**: тесты
   исключены из build-конфигов, а типизированный eslint TS-ошибок не репортит.
9. **`scripts/gen-connectors.test.ts`** — дубль `kind` падает с обоими именами директорий;
   файл без `defineConnector` падает с именем директории; `kind ≠ имя директории` даёт ключ
   реестра по `kind`.
10. **`profiles/schema.test.ts`** — на синтетическом вкладе: валидный конфиг проходит;
    опечатка даёт issue с путём `config.<поле>`; неизвестный `kind` называет полученный вид и
    перечисляет известные.
11. **`profiles/_test.ts` не трогать.** Цель — нулевой дифф. Понадобился — форма записи
    поехала, и это повод остановиться и доложить, а не подправить.

### Как доказывается каждый критерий

- **AC #1** — транскрипт с коннектором-пустышкой плюс остающийся в репозитории тест из шага 10.
- **AC #2** — тест на сообщение; ошибка возникает в `parseProfile`, до `getConnector`, поэтому сети не касается.
- **AC #3** — две отдельные строки доказательства: рантайм (issue с путём `sources.0.config.<поле>`) и компайл-тайм. **Предел, который нельзя проглотить:** zod по умолчанию срезает неизвестные ключи, поэтому рантайм ловит опечатку только когда правильное поле обязательное; для опциональных работает лишь компайл-тайм-половина. По DoD #8 назвать это там же, где заявлена возможность.
- **AC #4** — красный `pnpm verify` на новой директории; второй кейс — смена `kind` без переименования директории.
- **AC #5** — юнит-тест плюс живой транскрипт с двумя реальными директориями.
- **AC #6 — текст критерия неизмерим буквально:** ветка E-006 сама меняет `profiles/schema.ts`, поэтому `git diff --name-only main` вернёт его при любом исходе. Измеримая форма — диффать пустышку относительно вершины ветки после коммита работы E-006. Галочку при таком расхождении по DoD #1 не ставить: транскрипт в отчёт, дословная замена формулировки — в `## Заметки`, решает владелец.

### Что показывается красным до починки

Головной кейс — **дубль `kind`**: сначала сборщик без проверки дублей (тест красный), потом
проверка (зелёный), оба транскрипта в отчёт. Второй красный **прямо на сегодняшнем коде**:
zod печатает `Invalid discriminator value. Expected 'rss'` — полученный вид не назван, так
что тест «сообщение содержит `nope`» краснеет без всяких подмен.

Самопроверка «сломай двумя способами»: (1) ослабить `config` до
`z.record(z.string(), z.unknown())` — обязан покраснеть тест на опечатку; (2) заставить
генератор писать `kind: <connector>.kind` вместо литерала — обязано покраснеть compile-time
утверждение из шага 8.

### Ограничения `z.discriminatedUnion` (проверено на zod 4.4.3)

1. Тип требует **непустой кортеж**; результат `.map()` — массив, поэтому без mapped-tuple не компилируется. Ноль коннекторов — ошибка типа, и генератор должен падать со внятным сообщением, а не эмитить пустой кортеж.
2. Карта дискриминанта строится **лениво**, при первом `parse` (см. шаг 3).
3. Каждый вариант обязан отдавать `propValues` — практически это `ZodObject`. Обёртка варианта в `.refine()`/`.transform()` их теряет. Правило для будущих коннекторов: вклад — плоский `{kind, configSchema}`, без пост-обработки.
4. Литерал `kind` — единственное, что держит автокомплит (см. отвергнутый рантайм-вариант).
