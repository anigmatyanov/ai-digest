# E-013: Тесты на PrismaRepo

## Цель

Подмена уникального ключа в любом upsert'е `PrismaRepo` краснит `pnpm test`, а не
обнаруживается через месяц удвоившимся выпуском.

## Контекст (читать перед началом, по порядку)

1. **Дефект, ради которого эпик существует.** `packages/db/src/prisma-repo.ts` — 358 строк,
   несущих всю идемпотентность продукта, и **ни одного теста**. Единственное доказательство —
   транскрипт живого прогона в `## Заметки` эпика E-007. Ревьюер сформулировал точно: замена
   `where: { sourceId_externalId: … }` на `where: { id }` пройдёт `pnpm verify` зелёной.
2. `.claude/rules/testing.md` § «Что тестом не ловится»: «Живой прогон — доказательство, но
   не гейт: он не оставляет в репозитории ничего, что покраснеет завтра». E-007 закрыт именно
   в этом состоянии, осознанно и с записью в заметках. Этот эпик закрывает разрыв.
3. `packages/db/src/client.test.ts` — образец теста в этом пакете, не требующего БД.
4. `test/setup/no-network.ts` подменяет `fetch`. **Важно:** `PrismaNeon` ходит через
   WebSocket, а не через `fetch`, поэтому существующий сетевой гард этот путь не видит —
   найдено тем же ревью. Тест, случайно открывший соединение, не будет пойман.
5. E-007 `## Заметки`, запись от 2026-08-29 про ревью — там перечислено, что именно
   доказано живьём и что осталось без гейта.

## Объём — карта файлов

- `packages/db/src/prisma-repo.test.ts` — новый.
- `packages/db/src/prisma-repo.ts` — только если контур не тестируется без правки формы
  (например, клиент придётся принимать через параметр).
- `packages/db/package.json` — если понадобится тестовая зависимость.
- `test/setup/no-network.ts` — если решение закрыть WebSocket-путь окажется в этом эпике.

## Вне объёма

- Тесты стадий и раннера. Здесь только репозиторий.
- Векторные запросы: их пока нет.
- E-011 (продолжение прогона по статусу). Он будет звать `listCandidates`, но это его работа.

## Критерии приёмки

- [x] КОГДА в любом `upsert` уникальный ключ заменён на `where: { id }`,
      ТО `pnpm test` краснеет, называя метод.
- [x] КОГДА транзакция вокруг переписывания join-таблицы разбита на два отдельных запроса,
      ТО тест краснеет — свойство «между delete и create нет окна» проверяется, а не
      подразумевается.
- [x] КОГДА `putRawItems` перестаёт возвращать персистентный id,
      ТО тест краснеет: на этом держатся все ссылки внутри прогона.
- [x] КОГДА `pnpm test` запущен без `DATABASE_URL` и без сети,
      ТО он зелёный и не открывает ни одного соединения — включая WebSocket, который
      нынешний сетевой гард не видит.
- [x] КОГДА тест прогоняется на коде до починки соответствующего дефекта,
      ТО он красный; транскрипт в отчёте по каждому кейсу.

## Верификация

```bash
pnpm verify
pnpm typecheck
```

## Границы

**Не тестируй Prisma.** Проверять надо форму вызова — какой ключ в `where`, что попало в
`create` против `update`, что вернулось наружу, — а не то, что Postgres соблюдает уникальный
индекс. Тест, поднимающий настоящую базу, здесь дороже пользы и уводит `pnpm test` в сеть.

**Фейковый клиент — не мок ради мока.** Если для проверки формы вызова приходится описывать
половину Prisma Client, это сигнал, что контур стоит вынести в чистую функцию, строящую
аргументы upsert'а, и тестировать её.

**Сетевой гард не покрывает WebSocket.** Если закрывать это здесь — сказать в отчёте, что
изменилось для всех остальных тестов; если не здесь — зафилить стабом.

## План реализации

Сверено с `## Границы` построчно; каждый пункт ниже называет, какую границу он держит.

### 1. Форма upsert'а выносится в чистые функции (граница «не мок ради мока»)

В `packages/db/src/prisma-repo.ts` появляется секция экспортируемых чистых функций,
строящих аргументы, — по одной на таблицу:

```
topicUpsertArgs(topic)                → Prisma.TopicUpsertArgs
sourceUpsertArgs(topicId, source)     → Prisma.SourceUpsertArgs
rawItemUpsertArgs(sourceId, item)     → Prisma.RawItemUpsertArgs
candidateUpsertArgs(topicId, cand)    → Prisma.CandidateUpsertArgs
cardUpsertArgs(card)                  → Prisma.CardUpsertArgs
issueUpsertArgs(topicId, issue)       → Prisma.IssueUpsertArgs
candidateRawItemRows(candidateId, rawItemIds) → строки join-таблицы
issueCardRows(issueId, cardIds)               → строки join-таблицы (position = индекс)
```

Методы репозитория начинают звать их вместо инлайн-литералов. Возвращаемый тип аннотирован
сгенерированным `Prisma.*UpsertArgs`, поэтому проверка полей `create`/`update` компилятором
не теряется — она просто переезжает внутрь функции.

Это прямо то, что `## Границы` предписывает вместо описывания половины Prisma Client:
`where`, `create` и `update` проверяются как обычные объекты, без клиента вообще.

### 2. Минимальный записывающий клиент — только для того, что не является аргументом

Два свойства из критериев не выражаются формой аргументов: «переписывание join-таблицы идёт
одной транзакцией» и «наружу возвращается персистентный id». Для них — фейк в самом
`prisma-repo.test.ts` (карта файлов не разрешает новый модуль), покрывающий ровно те 14 точек
входа, которые репозиторий трогает, и пишущий журнал вызовов.

Ключевая деталь: метод модели возвращает не промис, а «отложенную операцию» — объект, который
(а) thenable, поэтому `await` работает, и (б) может быть отдан в `$transaction` неразвёрнутым.
Журнал помечает каждую операцию `batched: true/false`. Разбиение транзакции на два `await`
меняет журнал наблюдаемо: записи `$transaction` в нём просто нет.

### 3. Тесты

- Таблично-параметризованный набор «на каком ключе стоит upsert» — по строке на метод, имя
  метода в названии кейса, поэтому подмена на `where: { id }` краснеет **называя метод**.
- `create` против `update` по каждой таблице: что попадает только в `create` (идентичность —
  `sourceId`/`externalId`, `topicId`/`canonicalUrlHash`, `firstSeenAt`, `fetchedAt`) и чего
  в `update` быть не должно (рантайм-состояние источника: `cursor`, `health`, счётчики —
  реконсиляция конфигурации не стирает то, что узнал прошлый прогон).
- `scoreBreakdown` при отсутствии значения — `Prisma.DbNull`, а не `null`.
- Транзакции: обе join-таблицы переписываются внутри `$transaction`, `deleteMany` перед
  `createMany`, ни одной операции join-таблицы вне транзакции.
- Возврат персистентного id: `putRawItems`/`putCandidates`/`putCards`/`putIssue` возвращают
  id строки, а не тот, что принёс вызывающий.
- `list*`: `where` сужен темой прогона, маппинг `Date → ISO` и `null → undefined`.

### 4. Сетевой гард учится видеть WebSocket

`test/setup/no-network.ts` (файл в карте) дополнительно подменяет `globalThis.WebSocket`.
Проверено по коду `@neondatabase/serverless@1.1.0`: соединение открывается как
`new this.webSocketConstructor(url)` либо `new WebSocket(url)` — то есть через глобальный
конструктор, мимо `fetch`. Гард бросает тот же `NetworkAccessInTestError`, называя URL.

Радиус поражения для остальных тестов называется в отчёте отдельной строкой.

### 5. Красное по каждому критерию (DoD #7)

Диверсии, каждая — один транскрипт: подмена ключа в `where` на `{ id }`; разбиение
`$transaction` на два `await`; возврат `item.id` вместо `row.id`; снятие WebSocket-гарда.

### 2026-08-29 — исполнение E-013

**Что оказалось предметом теста.** Идемпотентность — это форма вызова, а форма вызова —
обычные данные. Аргументы всех шести upsert'ов и обеих join-таблиц вынесены в чистые
экспортируемые функции в `packages/db/src/prisma-repo.ts` (`topicUpsertArgs`,
`sourceUpsertArgs`, `rawItemUpsertArgs`, `candidateUpsertArgs`, `cardUpsertArgs`,
`issueUpsertArgs`, `candidateRawItemRows`, `issueCardRows`). Возвращаемый тип аннотирован
сгенерированным `Prisma.*UpsertArgs` минус `select`/`include`/`omit`, поэтому проверка полей
компилятором не потерялась — она переехала внутрь функции. Клиент для этих тестов не нужен
вообще.

**Что чистой функцией не выражается.** Два свойства из критериев не являются аргументами:
«join переписывается ОДНОЙ транзакцией» и «наружу уходит персистентный id». Для них в
`prisma-repo.test.ts` живёт записывающий фейк на те 14 точек входа, которые репозиторий
реально трогает. Его единственная нетривиальная деталь: метод модели возвращает не промис, а
объект, который одновременно thenable и может быть отдан в `$transaction` неразвёрнутым, —
как ведёт себя настоящий `PrismaPromise`. Поэтому разбиение транзакции на два `await`
наблюдаемо в журнале, а не только в Postgres.

**Сетевой гард теперь видит WebSocket.** `test/setup/no-network.ts` подменяет
`globalThis.WebSocket` тем же `NetworkAccessInTestError`. Измерено на живом адаптере (без
единого пакета наружу): `PrismaNeon` → `new WebSocket(...)` ловится гардом, дальше
`@neondatabase/serverless` глотает исключение в собственном `try/catch` и уходит на
fetch-фолбэк, где его ловит уже существующий гард. То есть один стаб не открывает сокет, а
второй печатает ошибку — нужны оба. Радиус для остальных тестов: любой тест, конструирующий
WebSocket, теперь падает; таких нет.

**Проверка на самом гарде.** Тест, который сам конструирует WebSocket, ходит на
`ws://127.0.0.1:9` намеренно: в день, когда гард сломают, единственный открывающий сокет тест
не должен стать той утечкой, ради которой он написан.

**Найдено и зафилено:** `docs/epics/E-013a-card-id-minted-by-database.md` — `cards` осталась
единственной таблицей, чей первичный ключ приносит пайплайн, и `extract` строит
`card-<candidateId>` без `techniqueKey`, который входит в уникальный ключ. Сегодня карточка
на кандидата одна, поэтому дефект латентный; вторая даст коллизию PK — тот же класс, что
ревью E-007 уже дважды чинило. Не починено здесь: карта файлов E-013 разрешает править
`prisma-repo.ts` ради тестируемости, а это изменение поведения.
