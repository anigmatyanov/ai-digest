# E-002: Чтение HTML-источников через Jina Reader с fallback

## Цель

Источник без RSS читается через Jina Reader, а при её недоступности — прямым fetch, и порядок этих попыток задаётся профилем, а не кодом.

## Контекст (читать перед началом, по порядку)

1. `packages/core/src/connector.ts` (создаётся в E-001) — контракт коннектора; сюда добавляется упорядоченный список бэкендов.
2. [.claude/rules/pipeline.md](../../.claude/rules/pipeline.md) — три обязательные вещи коннектора и правило «источник, отдающий ноль, обязан падать».
3. Идея заимствована из `Panniantong/agent-reach` (`agent_reach/channels/base.py`): «`backends` — упорядоченный список кандидатов, `backends[0]` предпочтительный, остальные fallback; переключить бэкенд значит переупорядочить список, а не переписать код». Оттуда же полезное предупреждение: наличие инструмента не есть доказательство его работоспособности — прежде чем объявлять бэкенд активным, надо реально выполнить лёгкий запрос.

### Измерено 2026-08-25, переоткрывать не нужно

- `GET https://r.jina.ai/<url>` — без API-ключа, HTTP 200.
- Лимит без ключа: заголовок `x-ratelimit-limit: 20, 20;w=60` — 20 запросов в минуту. Для еженедельного прогона с ~25 источниками с большим запасом.
- Латентность ~1.1 с против ~0.47 с у прямого запроса.
- `https://r.jina.ai/https://www.anthropic.com/news` → чистый markdown, **12** ссылок вида `/news/<slug>`. Это отменяет план писать свой SSR-парсер Anthropic.
- `https://r.jina.ai/https://t.me/s/data_secrets` → HTTP 200, **15** постов. Это отменяет план писать свой HTML-парсер Telegram.
- Ключевое архитектурное следствие: к целевому сайту ходит инфраструктура Jina, а не мы, поэтому блокировка датацентровых IP GitHub Actions обходится без прокси.

## Объём — карта файлов

- `packages/core/src/connector.ts` — добавление `backends` и `resolveBackend`
- `packages/core/src/types.ts`, `packages/core/src/schema/`
- `packages/connectors/src/backends/` — `jina.ts`, `direct-fetch.ts`
- `packages/connectors/src/html/` — коннектор HTML-источника поверх бэкендов
- `profiles/schema.ts` — поле порядка бэкендов у источника
- `fixtures/jina/`, `fixtures/html/`

## Вне объёма

- Коннекторы конкретных площадок (Anthropic news, Telegram) — отдельные эпики, они станут тривиальными после этого.
- Платный тир Jina и работа с API-ключом — пока не нужны, лимита хватает.
- Замена уже работающих путей: RSS, HN и GitHub `.atom` продолжают ходить напрямую. Jina включается только там, где альтернатива — свой хрупкий парсер.

## Критерии приёмки

- [ ] КОГДА источник объявлен с `backends: [jina, direct]`, ТО чтение идёт через Jina, и в отчёте прогона видно, какой бэкенд обслужил запрос
- [ ] КОГДА Jina в фикстуре отвечает 429 или 5xx, ТО коннектор прозрачно переходит на `direct` и помечает бэкенд деградировавшим — прогон не падает
- [ ] КОГДА оба бэкенда недоступны, ТО поднимается `SourceUnavailableError` с указанием обоих испробованных бэкендов
- [ ] КОГДА порядок в профиле изменён на `[direct, jina]`, ТО меняется фактический порядок попыток, и это подтверждается тестом без правки кода коннектора
- [ ] КОГДА фикстура ответа Jina не содержит ожидаемого поля, ТО поднимается `SourceDriftError` с именем поля — а не молчаливый ноль элементов
- [ ] КОГДА выполнен `pnpm verify`, ТО typecheck, lint и тесты зелёные при выключенной сети

## Верификация

```bash
pnpm verify
pnpm test -- backends
pnpm build && pnpm build:proof
pnpm connector:check html   # живой прогон: наблюдение, не гейт
```

Красный прогон fallback (DoD #7 — гейт обязан быть показан красным):

```bash
# подменить фикстуру Jina на 429 и убедиться, что бэкенд переключился, а не упал
pnpm test -- backends.fallback
```

## Границы

**Никогда:** ходить в сеть из тестов; делать Jina единственным путём для источника, у которого есть рабочий прямой доступ; хранить ключ Jina (на этом лимите он не нужен).

**Спросить заранее:** любое расширение карты файлов; добавление платного тира Jina; изменение порядка бэкендов у уже работающего источника.
