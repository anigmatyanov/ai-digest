# E-007: Персистентность прогона в Neon

## Цель

Прогон, убитый на середине, перезапускается и доводит выпуск до конца, не создавая дублей и
не оплачивая заново уже сделанные вызовы модели.

## Контекст (читать перед началом, по порядку)

1. `packages/core/src/pipeline/memory-repo.ts` — интерфейс, который надо реализовать поверх
   БД. `Repo` объявлен в `packages/core/src/pipeline/stage.ts`; **менять его сигнатуру в этом эпике
   нельзя** (см. Границы).
2. `packages/db/src/index.ts` — сейчас пуст по сути. Prisma-схемы в репозитории нет.
3. CLAUDE.md § Архитектура пайплайна: «работа выбирается по статусу строки, а не по номеру
   шага». Это и есть требование, ради которого нужна БД: без персистентного статуса
   перезапуск начинается с нуля и платит второй раз.
4. `docs/setup.md` § Neon — pooled `DATABASE_URL` для приложения и unpooled
   `DATABASE_URL_UNPOOLED` для миграций. **Перепутать их — типичная и дорогая ошибка:**
   миграция через пул виснет или ломается на середине.
5. `packages/core/src/env.ts` — единственное место, где читается `process.env`, проверяется
   линтером. Новые переменные приходят сюда.

## Объём — карта файлов

- `packages/db/prisma/schema.prisma` — модели и уникальные ключи.
- `packages/db/prisma/migrations/**` — первая миграция, включая `CREATE EXTENSION vector`.
- `packages/db/src/**` — клиент, `PrismaRepo`, изоляция сырого SQL для векторов.
- `packages/core/src/env.ts` — `DATABASE_URL`, `DATABASE_URL_UNPOOLED`.
- `.env.example`
- `apps/pipeline/src/run.ts` — выбор репозитория: БД по умолчанию, `MemoryRepo` под
  `--fixtures`.
- `package.json` — скрипт `db:status` и миграционные команды.

## Вне объёма

- Векторные операции и pgvector-поиск. Расширение ставится миграцией, колонка заводится,
  запросы — отдельный эпик вместе с дедупликацией.
- Ретеншн. Отдельный эпик; здесь достаточно, чтобы схема его не исключала.
- Стадии. Ни одна не переписывается: они разговаривают с `ctx.repo` и не знают, что за ним.
- Публикация и `Delivery`.

## Критерии приёмки

- [ ] КОГДА прогон убит между стадиями и запущен заново,
      ТО он продолжает с сохранённого состояния, и число строк в `RawItem` и `Candidate`
      после второго прогона совпадает с числом после первого.
- [ ] КОГДА один и тот же элемент источника приходит дважды,
      ТО в `RawItem` остаётся одна строка — идемпотентность обеспечена уникальным ключом
      `(sourceId, externalId)`, а не проверкой в коде.
- [ ] КОГДА одна новость пришла из двух разных источников с одинаковым каноническим URL,
      ТО кандидат один — уникальный ключ `(topicId, canonicalUrlHash)`.
- [ ] КОГДА `pnpm digest:run --fixtures` запущен без `DATABASE_URL`,
      ТО прогон работает на `MemoryRepo` и не пытается открыть соединение: офлайн-путь
      остаётся офлайн-путём.
- [ ] КОГДА `DATABASE_URL` задан, но недоступен,
      ТО ошибка называет, какая из двух строк подключения использовалась и для чего.
- [ ] КОГДА миграция применяется к пустой базе,
      ТО `vector` создаётся до первой таблицы, которая на него ссылается.
- [ ] КОГДА `pnpm test` запущен при неустановленном `DATABASE_URL`,
      ТО он зелёный: тесты не открывают соединение ни при каком раскладе.

## Верификация

```bash
pnpm verify
pnpm digest:run --profile profiles/dist/_test.js --fixtures --dry-run   # MemoryRepo, без БД
pnpm db:status
pnpm golden
```

Прогон против ветки Neon этого worktree — руками, с владельцем: `live-effects-guard.sh`
блокирует миграции из агентской сессии, и это правильно.

## Границы

**Сигнатура `Repo` не меняется.** Она живёт в `stage.ts` под меткой `pipeline-contract`, и
этот эпик её не держит — значит параллельная ветка может её править. Если реализация
упирается в интерфейс, это находка и стаб-эпик, а не расширение объёма на ходу.

**Один автомат состояний — на `Candidate`.** `Card` — payload, а не второй автомат: два
независимых статуса рассинхронизируются на первом же ретрае. Соблазн завести `Card.status`
возникнет; это то же решение, что уже принято, а не новое.

**Векторные поля Prisma Client не читает.** `Unsupported("vector(384)")` доступен только
через `$queryRaw`, и весь сырой SQL изолируется в одном модуле — иначе он расползётся.

**Миграции — через unpooled-строку.** Не «желательно», а условие корректности.
