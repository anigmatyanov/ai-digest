# E-007: Персистентность прогона в Neon

## Цель

Прогон, убитый на середине, перезапускается и доводит выпуск до конца, не создавая дублей и
не оплачивая заново уже сделанные вызовы модели.

## Контекст (читать перед началом, по порядку)

1. `packages/core/src/pipeline/memory-repo.ts` — интерфейс, который надо реализовать поверх
   БД. `Repo` объявлен в `packages/core/src/pipeline/stage.ts`; **менять его сигнатуру в этом эпике
   нельзя** (см. Границы).
2. `packages/db/src/index.ts` — сейчас пуст по сути. Prisma-схемы в репозитории нет.
3. CLAUDE.md § Архитектура пайплайна: «работа выбирается по статусу строки, а не по номеру
   шага». Это и есть требование, ради которого нужна БД: без персистентного статуса
   перезапуск начинается с нуля и платит второй раз.
4. `docs/setup.md` § Neon — pooled `DATABASE_URL` для приложения и unpooled
   `DATABASE_URL_UNPOOLED` для миграций. **Перепутать их — типичная и дорогая ошибка:**
   миграция через пул виснет или ломается на середине.
5. `packages/core/src/env.ts` — единственное место, где читается `process.env`, проверяется
   линтером. Новые переменные приходят сюда.

## Объём — карта файлов

- `packages/db/prisma/schema.prisma` — модели и уникальные ключи.
- `packages/db/prisma/migrations/**` — первая миграция, включая `CREATE EXTENSION vector`.
- `packages/db/src/**` — клиент, `PrismaRepo`, изоляция сырого SQL для векторов.
- `packages/core/src/env.ts` — `DATABASE_URL`, `DATABASE_URL_UNPOOLED`.
- `.env.example`
- `apps/pipeline/src/run.ts` — выбор репозитория: БД по умолчанию, `MemoryRepo` под
  `--fixtures`.
- `package.json` — скрипт `db:status` и миграционные команды.

## Вне объёма

- Векторные операции и pgvector-поиск. Расширение ставится миграцией, колонка заводится,
  запросы — отдельный эпик вместе с дедупликацией.
- Ретеншн. Отдельный эпик; здесь достаточно, чтобы схема его не исключала.
- Стадии. Ни одна не переписывается: они разговаривают с `ctx.repo` и не знают, что за ним.
- Публикация и `Delivery`.

## Критерии приёмки

- [ ] КОГДА прогон убит между стадиями и запущен заново,
      ТО он продолжает с сохранённого состояния, и число строк в `RawItem` и `Candidate`
      после второго прогона совпадает с числом после первого.
- [x] КОГДА один и тот же элемент источника приходит дважды,
      ТО в `RawItem` остаётся одна строка — идемпотентность обеспечена уникальным ключом
      `(sourceId, externalId)`, а не проверкой в коде.
- [x] КОГДА одна новость пришла из двух разных источников с одинаковым каноническим URL,
      ТО кандидат один — уникальный ключ `(topicId, canonicalUrlHash)`.
- [x] КОГДА `pnpm digest:run --fixtures` запущен без `DATABASE_URL`,
      ТО прогон работает на `MemoryRepo` и не пытается открыть соединение: офлайн-путь
      остаётся офлайн-путём.
- [x] КОГДА `DATABASE_URL` задан, но недоступен,
      ТО ошибка называет, какая из двух строк подключения использовалась и для чего.
- [x] КОГДА миграция применяется к пустой базе,
      ТО `vector` создаётся до первой таблицы, которая на него ссылается.
- [x] КОГДА `pnpm test` запущен при неустановленном `DATABASE_URL`,
      ТО он зелёный: тесты не открывают соединение ни при каком раскладе.

## Верификация

```bash
pnpm verify
pnpm digest:run --profile profiles/dist/_test.js --fixtures --dry-run   # MemoryRepo, без БД
pnpm db:status
pnpm golden
```

Прогон против ветки Neon этого worktree — руками, с владельцем: `live-effects-guard.sh`
блокирует миграции из агентской сессии, и это правильно.

## Границы

**Сигнатура `Repo` не меняется.** Она живёт в `stage.ts` под меткой `pipeline-contract`, и
этот эпик её не держит — значит параллельная ветка может её править. Если реализация
упирается в интерфейс, это находка и стаб-эпик, а не расширение объёма на ходу.

**Один автомат состояний — на `Candidate`.** `Card` — payload, а не второй автомат: два
независимых статуса рассинхронизируются на первом же ретрае. Соблазн завести `Card.status`
возникнет; это то же решение, что уже принято, а не новое.

**Векторные поля Prisma Client не читает.** `Unsupported("vector(384)")` доступен только
через `$queryRaw`, и весь сырой SQL изолируется в одном модуле — иначе он расползётся.

**Миграции — через unpooled-строку.** Не «желательно», а условие корректности.

### 2026-08-29 — состояние на конец сессии владельца

Отмечены два критерия из семи. Остальные пять требуют применённой миграции, а её применение
блокируется `live-effects-guard.sh` из агентской сессии — это и есть та часть, ради которой
эпик помечен `paired`.

**Доказано:**

- Критерий 4 — в **более сильной** форме, чем записан: `DATABASE_URL` был установлен в `.env`,
  и прогон всё равно пошёл через `MemoryRepo`. То есть офлайн-путь выбирается по флагу
  `--fixtures`, а не по отсутствию переменной, и не может «случайно» подключиться на машине,
  где переменная есть.
- Критерий 7 — 72 теста зелёные при спрятанном `.env` и снятых обеих переменных
  (транскрипт в отчёте). `.env` восстановлен.
- Половина критерия 5: перепутанные строки подключения ловятся при конструировании клиента,
  а не при первом запросе. `packages/db/src/client.test.ts` краснеет, если убрать проверку
  `-pooler`. Вторая половина — поведение при недоступной базе — не проверена, поэтому
  галочка не ставится.
- Порядок в миграции: `CREATE EXTENSION vector` стоит перед первой таблицей с колонкой
  `vector(384)`. Проверка вынесена в `scripts/lib/migration-checks.mjs` и покрыта пятью
  тестами, включая красный на перевёрнутом порядке и на полном отсутствии расширения.
  Но критерий 6 говорит «применяется к пустой базе» — этого не было, галочки нет.

**Что осталось владельцу:**

```bash
cd packages/db && ./node_modules/.bin/prisma migrate deploy   # применить к ветке Neon
pnpm db:status                                                 # офлайн-часть отчёта
```

После этого критерии 1, 2, 3 и 6 проверяются живым прогоном, а 5 — временной подменой
`DATABASE_URL` на недоступный хост.

**Найдено по дороге, вне карты файлов (починено отдельными коммитами на `main`, не в этой ветке):**

1. `prisma@latest` резолвится в **8.0.0-rc.12** при `@prisma/client@latest` = 7.10.0. CLI и
   клиент обязаны совпадать; обе версии запинены на 7.10.0.
2. `live-effects-guard.sh` дважды ложно блокировал read-only команды (`prisma migrate diff
   --from-empty`, и до того `gh api`). Во второй правке нашлась дыра: `--from-config-datasource`
   подключается к базе и проходил. Закрыто, доказано красным против предыдущего коммита.
3. `pnpm lint` в главном дереве читал worktree работающих агентов — 393 ошибки из чужих
   незавершённых веток. `.claude/worktrees/**` добавлен в ignore линтера и prettier.
4. `pnpm format` ломал `pnpm verify`: `prettier --check` был красным на генерируемом
   `registry.ts`, а `--check` генератора сравнивает побайтово.
5. `pnpm install` выходил с кодом 1 из-за нерешённых build-скриптов, и это валило **любой**
   pnpm-скрипт (pnpm делает install-проверку перед запуском). Решения записаны явно в
   `pnpm-workspace.yaml` с обоснованием по каждому пакету.

**Предложение по правилам (применяет владелец, DoD #12):** в
[.claude/rules/pipeline.md](../../.claude/rules/pipeline.md) стоит добавить строку о том,
что офлайн-путь выбирается флагом `--fixtures`, а не отсутствием `DATABASE_URL` — сейчас об
этом сказано только в комментарии в коде.

### 2026-08-29 (позже) — миграция применена, шесть критериев из семи

Владелец разрешил разовый обход гарда, миграция применена к ветке Neon `main` через
**direct**-хост. Дальше — живой прогон, и он нашёл то, чего фикстуры найти не могли.

**Дефект, найденный живым прогоном: пайплайн не сохранял ни `RawItem`, ни `Candidate`.**
Сохранялись только карточки. С `MemoryRepo` это было невидимо — у Map нет ссылочной
целостности, поэтому карточки годами могли ссылаться на кандидатов, которых нигде нет.
Postgres отверг это сразу: `cards_candidateId_fkey`, затем `candidate_raw_items_rawItemId_fkey`.
Добавлены шаги `persist-raw` и `persist-candidates`; идентификаторы пайплайна сохраняются
при вставке, иначе ссылки внутри одного прогона рвутся.

**Идемпотентность (критерии 1-частично, 2, 3):**

```
после 1-го прогона: {"topics":1,"sources":1,"raw_items":6,"candidates":6,"candidate_raw_items":6,"cards":4}
после 2-го прогона: {"topics":1,"sources":1,"raw_items":6,"candidates":6,"candidate_raw_items":6,"cards":4}
```

Критерий 3 отдельно: две записи одного `canonicalUrlHash` из разных источников дают
**одну** строку, первый id сохраняется, поля обновляются.

**Критерий 5 был показан красным в самой неприятной форме.** Недоступная база бросает
`ErrorEvent` с **пустым** `message` — не плохое сообщение, а его отсутствие. Прогон умирал
бы пустой строкой. Теперь первое обращение к БД обёрнуто, и ошибка называет хост, какая из
двух строк подключения использовалась и что обычно бывает причиной. Названный предел:
обёрнут только `PrismaRepo.open` — обрыв связи в середине прогона по-прежнему приходит
ошибкой адаптера, потому что оборачивать каждый запрос значило бы похоронить те, что
говорят по делу (нарушение констрейнта называет свой констрейнт).

**Критерий 1 НЕ отмечен, и это не формальность.** Доказана его вторая половина —
повторный прогон не создаёт дублей. Первая половина, «продолжает с сохранённого состояния»,
не реализована: второй прогон переделывает все стадии заново. На фикстурах это бесплатно,
на живом прогоне это вторая оплата `extract`. Зафилено как **E-011**.

**Добавлен флаг `--db`.** `--fixtures` управлял сразу двумя вещами — записанными ответами
модели и репозиторием в памяти, — из-за чего проверить базу можно было только заплатив за
живые вызовы модели. Теперь это два независимых выбора, а умолчание осталось полностью
офлайновым.

### 2026-08-29 (ревью) — две критические находки на собственной работе

Эпик `paired`, его делала главная сессия, поэтому ревью отдано свежему контексту: исполнитель
не оценивает свою работу. Ревьюер нашёл два критических дефекта, оба настоящие, оба починены.

**1. Идентификатор пайплайна использовался как первичный ключ.** `normalize` строит
`cand-<первые 12 hex канонического хеша>` — то есть **усечение того же ключа**, по которому
идёт upsert, и без темы, которую ключ содержит. Два пути столкновения: одна статья в двух
темах промахивается по `where`, уходит в `create` и падает на PK; и 48 бит сталкиваются по
парадоксу дней рождения примерно на 24 тысячах кандидатов. То же для `raw-<sourceKey>-<id>`.
Теперь id выдаёт база, а ссылки внутри прогона разрешаются потому, что методы возвращают
персистентную строку. Проверено: после смены схемы id два прогона подряд не создали ни одной
новой строки — существующие нашлись по уникальному ключу, а не по id.

**2. Переписывание join-таблицы шло двумя запросами без транзакции.** Сбой между `deleteMany`
и `createMany` оставлял кандидата с нулём raw items — строка, нарушающая
`rawItemIds: z.array(...).min(1)` из `domain.ts`. Ровно тот класс «данные проходят typecheck
и умирают на границе стадии», против которого написана шапка `schema.prisma`. Обе таблицы
переписываются в одной транзакции.

**Плюс пять предупреждений, тоже починены:**

- `catch` в `PrismaRepo.open` ловил всё и переводил в «база недоступна, вы наверное перепутали
  строки подключения». Неприменённая миграция (P2021) отправляла бы читателя проверять не то.
  Ошибка с кодом — это база **отвечающая**, она пробрасывается как есть.
- `Card` не имел ни одного уникального ключа кроме PK: идемпотентность карточек держалась на
  том, что `extract` строит детерминированный id. Соглашение, а не констрейнт — при том что
  шапка схемы утверждает обратное. Добавлен `@@unique([candidateId, techniqueKey])` и вторая
  миграция.
- `includes("-pooler")` проверял всю строку подключения, а не хост: пароль или параметр с
  такой подстрокой пропустил бы direct-хост. `db-status.mjs` делал это правильно — две
  реализации одного правила разошлись.
- `vectorOrderingProblem` судил каждую миграцию отдельно, поэтому вторая миграция с
  vector-колонкой (расширение создано первой) покраснела бы на корректном наборе.
- `--db` без `--fixtures` молча выбирает живой платный gateway. Теперь предупреждает.

**Не сделано осознанно:**

- Тестов на `PrismaRepo` нет. 358 строк идемпотентного контура доказаны живым прогоном, то
  есть транскриптом, а не гейтом: подмена `where` на `id` прошла бы `pnpm verify` зелёной.
  Это настоящий пробел, и он не закрывается в рамках этого эпика — нужен либо фейковый
  `PrismaClient`, либо pglite. Отдельная работа.
- `listRawItems`, `listCandidates`, `putIssue` не вызываются ни разу. Написаны, не исполнены.
  Их первый потребитель — E-011.
- Схема шире zod в нескольких местах (статусы как `String` без CHECK, `score` без границ,
  длины списков). Осознанно: кривая строка сохранится и упадёт на чтении, а не при записи.
