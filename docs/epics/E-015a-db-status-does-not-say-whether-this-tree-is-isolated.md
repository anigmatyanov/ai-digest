# E-015a: провал изоляции базы виден только тому, кто читал deny-сообщение

## Цель

Агент, работающий в worktree без изолированной базы, узнаёт об этом из команды, а не из
сообщения хука, которое проехало мимо два часа назад.

## Контекст (читать перед началом, по порядку)

1. E-015 сделал слотовый `.env` реальным файлом со строками своей ветки Neon. Когда
   `neonctl` недоступен, `DATABASE_URL` в нём **отсутствует** — это правильное поведение, но
   единственный сигнал о нём — строка `db:` в одноразовом deny-сообщении хука.
2. Измерено 2026-08-29 в ходе E-015: `neonctl` при истёкшем refresh-токене печатает
   `Authentication failed, deleting credentials...`, **удаляет** `~/.config/neon/credentials.json`
   и уходит ждать браузер. С этого момента каждый следующий слот получает `.env` без
   `DATABASE_URL`, и ничто про это не напоминает.
3. `scripts/db-status.mjs` — единственная команда, которая смотрит на конфигурацию базы. Её
   собственная секция «What this cannot tell you» честно говорит, что она не знает, на какую
   ветку Neon смотрит. Внутри worktree это ровно тот вопрос, который нужен.
4. Файл вне карты E-015, поэтому зафилен стабом, а не поправлен инлайн.

## Объём — карта файлов

- `scripts/db-status.mjs`
- `docs/setup.md` — если меняется то, что владелец делает руками.

## Вне объёма

- Автоматический `neonctl auth`: это действие наружу и требует браузера.
- Перевыдача `.env` уже живущему worktree.

## Критерии приёмки

- [ ] КОГДА `pnpm db:status` запущен внутри `.claude/worktrees/<slug>`, ТО отчёт называет,
      что это слот, и изолирован ли его `DATABASE_URL` от главного дерева.
- [ ] КОГДА в слотовом `.env` нет `DATABASE_URL`, ТО `pnpm db:status` называет причину
      (ветка Neon не провижинилась) и команду восстановления, а не только «is not set».
- [ ] КОГДА `pnpm db:status` запущен в главном дереве, ТО его вывод не меняется.

## Верификация

```bash
pnpm verify
node scripts/db-status.mjs
```

## Границы

**Никогда:** печатать строку подключения; звать `neonctl auth`; трогать файлы вне карты.
