# E-013a: id карточки минтит база

## Цель

Вторая карточка одного кандидата сохраняется, а не падает на коллизии первичного ключа.

## Контекст (читать перед началом, по порядку)

1. `packages/db/src/prisma-repo.ts`, `cardUpsertArgs` — `create: { ...data, id: card.id }`.
   Это единственная из трёх таблиц, где первичный ключ приносит пайплайн: у `raw_items` и
   у `candidates` его отобрали в ревью E-007 ровно за этот класс дефекта.
2. `packages/core/src/pipeline/stages/extract.ts:244` — `id: \`card-${candidate.id}\``.
   Идентификатор **не содержит `techniqueKey`**, а уникальный ключ таблицы —
   `@@unique([candidateId, techniqueKey])`, то есть домен прямо допускает несколько карточек
   на кандидата. Сегодня `extract` кладёт ровно одну, поэтому дефект латентный.
3. `packages/db/prisma/schema.prisma`, модель `Card` — комментарий к `@@unique` объясняет,
   почему идемпотентность карточек не должна держаться на форме id, которую строит стадия.
4. E-007 `## Заметки`, запись «две критические находки» — тот же дефект, разобранный для
   `raw_items` и `candidates`, с описанием обоих путей столкновения.

## Объём — карта файлов

- `packages/db/src/prisma-repo.ts` — `cardUpsertArgs`.
- `packages/db/src/prisma-repo.test.ts` — кейс на два техника-ключа одного кандидата.
- `packages/core/src/pipeline/stages/extract.ts` — только если окажется, что стадии всё ещё
  нужен собственный id до записи.

## Вне объёма

- Разрешение `extract` отдавать больше одной карточки на кандидата. Это отдельное
  продуктовое решение; здесь чинится только то, что репозиторий такой вход не переживёт.
- Миграция. Схема уже несёт нужный уникальный ключ.

## Критерии приёмки

- [ ] КОГДА `putCards` получает две карточки одного `candidateId` с разными `techniqueKey`,
      ТО обе сохраняются, и тест это показывает.
- [ ] КОГДА `extract` меняет схему построения id карточки,
      ТО ни один upsert не меняет поведения — тест на это красный до починки.
