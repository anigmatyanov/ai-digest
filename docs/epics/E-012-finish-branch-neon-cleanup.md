# E-012: Уборка Neon-ветки на мерже проходит без обхода гарда

## Цель

Шаг уборки из `/finish-branch` выполняется без `ALLOW_LIVE_EFFECTS=1`, а удаление любой
другой ветки Neon по-прежнему отклоняется.

## Контекст (читать перед началом, по порядку)

1. **Дефект, ради которого эпик существует.** 2026-08-29, при мерже E-005:
   `.claude/commands/finish-branch.md` шаг 4 предписывает
   `neonctl branches delete "$BR"`, а `.claude/hooks/live-effects-guard.sh` отклоняет её
   безусловно — с сообщением «/finish-branch removes the slot's branch when the work
   merges. Nothing else should delete one». То есть гард ссылается на процесс, которому сам
   не даёт выполниться. Пришлось обойти разрешением владельца.
2. `.claude/hooks/live-effects-guard.sh` — блок про `neonctl ... delete`. Там же рядом два
   уже сделанных carve-out'а (read-only verbs `neonctl`, `gh api` GET) — образец формы и
   образец того, как carve-out дисквалифицируется.
3. `.claude/commands/finish-branch.md` — порядок шагов. Удаление Neon-ветки идёт **после**
   `git worktree remove` и освобождения слота, и это существенно: к моменту удаления
   ни worktree, ни слота для этой ветки уже не существует.
4. Прецедент: `git-branch-delete-guard.sh` решает ровно такую же задачу для git-веток —
   разрешает удаление, если работа ветки уже на `main`. Логика проверки, а не согласования.
5. Второй заход того же дефекта, замеченный при заведении этого эпика: гард отклонил
   **сообщение коммита**, которое описывает проблему, потому что в нём цитируется команда.
   «Называние субъекта не есть действие» — у гарда уже есть carve-out'ы ровно этого класса
   (`grep -rn publish`, `cat vercel.json`, `pnpm --filter .../telegram add`), и это ещё один
   его случай. Стоит закрыть заодно: судить только первый сегмент команды, а не весь текст
   `-m`/`-F`.

## Объём — карта файлов

- `.claude/hooks/live-effects-guard.sh` — carve-out.
- `test/hooks/run.sh` — кейсы.
- `.claude/commands/finish-branch.md` — если формулировка шага должна измениться.

## Вне объёма

- `neonctl projects delete` и `databases delete`. Они остаются запрещёнными безусловно.
- Удаление удалённой git-ветки (`git push origin --delete`). Отдельный случай, остаётся в
  `permissions.deny`.
- Автоматическая уборка осиротевших веток Neon. Отдельная задача.

## Критерии приёмки

- [x] КОГДА удаляется ветка Neon вида `agent/<slug>`, для которой в `git worktree list` нет
      worktree и нет каталога слота, ТО команда проходит.
- [x] КОГДА удаляется ветка Neon, для которой worktree ещё существует,
      ТО команда отклоняется — это живая работа соседа.
- [x] КОГДА удаляется `main` или любая ветка не по шаблону `agent/<slug>`,
      ТО команда отклоняется.
- [x] КОГДА удаляется проект или база (`projects delete`, `databases delete`),
      ТО команда отклоняется независимо от имени.
- [x] КОГДА новый кейс прогоняется на коде до починки,
      ТО первый краснеет, а остальные три остаются зелёными — carve-out не стал байпасом.

## Границы

**Carve-out не должен становиться префиксом.** Проверять надо не только имя ветки, но и
отсутствие живого worktree — иначе достаточно назвать ветку `agent/что-угодно`, чтобы снести
чужую базу. Это тот же урок, что уже записан рядом про `pnpm install && ...`.

**Проверка по состоянию, а не по намерению.** Гард не может узнать, что его вызвал
`/finish-branch`. Единственный надёжный признак — что уборка уже произошла: worktree снят,
слот освобождён. На это и опираться.

## План реализации

Сверено с `## Границы`: обе записи там — «проверять состояние, а не имя» и «carve-out не
должен становиться префиксом» — определяют шаги 2 и 3 ниже. Расхождений с границами нет.

**1. Где живёт carve-out.** Прямо перед существующим deny про `neonctl ... delete` в
`live-effects-guard.sh`. Позиция нагружена смыслом: к этой строке фазы 2 все прочие deny
(`digest:run`, `--publish`, `vercel`, `gh workflow run`, `gh secret`, `prisma migrate`) уже
отработали, поэтому команда, приделавшая к удалению ветки чужой эффект, до carve-out просто
не доходит. Это и есть ответ на «не должен становиться префиксом» — не новая проверка, а
порядок, который уже есть.

**2. Признак — состояние, а не имя.** Разрешаем удаление, только если для КАЖДОГО имени,
названного в `neonctl branches delete`, выполнено всё:

- имя матчит `^agent/[a-z0-9][a-z0-9._-]*$` (`main`, `production`, `agent/../x` — мимо);
- в `git worktree list --porcelain` нет строки `branch refs/heads/<имя>`;
- в `<главное дерево>/.claude/worktrees/.slots/*/branch` нет файла с этим именем.

Главное дерево берётся первой записью `git worktree list --porcelain`, а не `$REPO_ROOT`:
хук физически лежит внутри worktree исполнителя, а каталог слотов — только в главном дереве.

Дисквалификаторы, снимающие carve-out целиком: `neonctl projects delete`,
`neonctl databases delete`, любой другой мутирующий глагол `neonctl` в той же команде, а
также невозможность извлечь хоть одно имя (fail-closed).

**3. Имя обязано быть литеральным.** `neonctl branches delete "$BR"` хук разрешить не может
и не должен: `$BR` — это переменная вызывающей оболочки, и «проверка по состоянию»
превращается в угадывание. Поэтому шаг 4 `.claude/commands/finish-branch.md` переписывается
на литеральное `agent/<slug>` (остальные строки шага уже так и написаны), с одной фразой
о том, почему литерал здесь обязателен.

**4. Второй дефект (`## Контекст` п. 5) — судить исполняемый текст.** Перед фазой 1
команда приводится к «судимому» виду двумя проходами awk:

- **тело heredoc'а выбрасывается**, но только если терминатор реально найден дальше по
  тексту (иначе `1 << SHIFT` съел бы остаток команды) и только если heredoc не кормит
  интерпретатор (`bash <<EOF … EOF` остаётся судимым целиком);
- **закавыченный аргумент после `-m`/`--message`/`-F`/`--file` обнуляется.** Сканер идёт по
  всему тексту команды, а не построчно, иначе многострочное сообщение коммита теряется
  после первой строки.

Сам флаг при этом остаётся в тексте — дисквалификатор `gh api -F` продолжает срабатывать, а
`vercel deploy --prod -m "…"` продолжает блокироваться. Deny по-прежнему печатает исходную
команду, а не судимую.

**5. Батарея.** Кейс AC-1 — красный до починки. Кейс AC-2 требует ЖИВОГО worktree, поэтому
батарея заводит зонд `git worktree add --no-checkout` на ветке `agent/probe-live-worktree`
и удаляет его сразу после двух кейсов; зонд слота — просто каталог, как уже делают
`_probe_mine`/`_probe_other`. Имя зонда обязано быть валидным `agent/<slug>` — с ведущим
подчёркиванием кейс зеленел бы из-за формы имени, а не из-за живого worktree, то есть был бы
декоративным. Плюс кейсы на дисквалификаторы и на оба состояния второго дефекта.

**6. Что НЕ делается (стаб).** У гарда есть ещё три exemption'а, которые можно приделать
префиксом: read-only `^(cat|grep|…)`, `*--dry-run*` и `--help`. Это тот же класс, что уже
чинили для `pnpm install &&`, но он вне секции carve-out — филится стабом, а не правится
инлайн.

**2026-08-29, исполнитель.**

**Красный прогон (код до починки, новые кейсы уже в батарее).** Ровно тот раскол, который
требует AC-5:

```
FAIL  neon: an orphaned agent branch goes            want exit=0 got=2
FAIL  neon: the form finish-branch writes            want exit=0 got=2
FAIL  text: a commit message quoting a ban           want exit=0 got=2
FAIL  text: a multi-line commit message              want exit=0 got=2
FAIL  text: a heredoc body is data                   want exit=0 got=2
hook battery: 176 passed, 5 failed
```

Красные — только кейсы AC-1 и три кейса второго дефекта. Все кейсы AC-2/3/4 (живой worktree,
удерживаемый слот, `main`, `production`, `agent/../main`, `databases delete`, четыре
префиксных формы) до починки зелёные и после починки зелёные — это и есть доказательство,
что carve-out не стал дырой.

**Самопроверка «сломай починку двумя способами» дала две находки, а не подтверждение.**
Сломал шесть раз; четыре поймались, две — нет. Не поймались: (а) снятие проверки, что
терминатор heredoc'а реально существует дальше по тексту, и (б) снятие требования, чтобы
аргумент `-m` был закавычен. Обе — настоящие дыры: (а) даёт `echo "1 << SHIFT"` + опасная
строка следом, (б) даёт `-m --publish`, где обнуляется сам флаг, делающий прогон живым.
Добавлены два кейса, после чего краснеют все шесть. Батарея, зелёная на подломанной
починке, — это ровно тот случай, о котором написано в testing.md; здесь он случился.

**Живой прогон против настоящего состояния репозитория** (worktree'ы: main, E-006, E-012;
слоты 1 и 2 заняты):

```
neonctl branches delete "agent/e-005-bash-write-guard"    exit=0  (эпик смержен, worktree и слот сняты)
neonctl branches delete "agent/e-006-source-schema-codegen" exit=2 (живая работа соседа)
neonctl branches delete "agent/e-012-guard-carve-out"     exit=2  (собственный живой worktree)
neonctl branches delete "$BR"                             exit=2  (имя не резолвится)
neonctl branches delete main                              exit=2
neonctl branches delete agent/e-005-… && vercel deploy --prod  exit=2 (deny про vercel, до carve-out)
```

**Находка, которой не было в эпике: `"$BR"` тихо снимал и вторую проверку.**
`.claude/commands/finish-branch.md` предписывал `git branch -D "$BR"`, а
`git-branch-delete-guard.sh` на нерезолвящемся имени говорит «is not a local branch — leaving
it to git» и выходит с 0. То есть автономная проверка «работа ветки уже на main», которую
`.claude/rules/backlog.md` описывает как замену согласованию с владельцем, при этой записи
шага не выполнялась вообще. Шаг 4 переписан на литеральный `agent/<slug>` для обеих команд,
с объяснением на месте.

**Стаб E-012a** — `docs/epics/E-012a-guard-exemptions-as-prefixes.md`. Три exemption'а
`live-effects-guard.sh` можно приделать префиксом к произвольной команде. Измерено, не
предположено:

```
cat README.md && vercel deploy --prod                              exit=0
pnpm digest:run --profile p.ts --fixtures --dry-run && vercel deploy --prod  exit=0
vercel deploy --prod ; echo --help                                 exit=0
vercel deploy --prod            (контроль, без префикса)           exit=2
```

Инлайн не правил: карта файлов E-012 сужает `live-effects-guard.sh` до секции carve-out'а, а
это три другие секции фазы 2.

**Rules retrospective — Proposal (дублируется в отчёт; применяет владелец).**
В `.claude/rules/backlog.md`, § «Удаление ветки — автономное действие», после абзаца про
`git-branch-delete-guard.sh` добавить:

> Команда, которую судит хук, пишется в `.claude/commands/*` с **литеральным** аргументом, а
> не через переменную. Хук видит текст команды, а не окружение вызывающей оболочки: на
> `git branch -D "$BR"` `git-branch-delete-guard.sh` не находит локальной ветки с таким
> именем, говорит «leaving it to git» и выходит с нулём. Проверка, которая здесь заменяет
> согласование с владельцем, при этом просто не выполняется — и по зелёному прогону это
> неотличимо от успешной проверки.
