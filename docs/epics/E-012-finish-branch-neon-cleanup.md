# E-012: Уборка Neon-ветки на мерже проходит без обхода гарда

## Цель

Шаг уборки из `/finish-branch` выполняется без `ALLOW_LIVE_EFFECTS=1`, а удаление любой
другой ветки Neon по-прежнему отклоняется.

## Контекст (читать перед началом, по порядку)

1. **Дефект, ради которого эпик существует.** 2026-08-29, при мерже E-005:
   `.claude/commands/finish-branch.md` шаг 4 предписывает
   `neonctl branches delete "$BR"`, а `.claude/hooks/live-effects-guard.sh` отклоняет её
   безусловно — с сообщением «/finish-branch removes the slot's branch when the work
   merges. Nothing else should delete one». То есть гард ссылается на процесс, которому сам
   не даёт выполниться. Пришлось обойти разрешением владельца.
2. `.claude/hooks/live-effects-guard.sh` — блок про `neonctl ... delete`. Там же рядом два
   уже сделанных carve-out'а (read-only verbs `neonctl`, `gh api` GET) — образец формы и
   образец того, как carve-out дисквалифицируется.
3. `.claude/commands/finish-branch.md` — порядок шагов. Удаление Neon-ветки идёт **после**
   `git worktree remove` и освобождения слота, и это существенно: к моменту удаления
   ни worktree, ни слота для этой ветки уже не существует.
4. Прецедент: `git-branch-delete-guard.sh` решает ровно такую же задачу для git-веток —
   разрешает удаление, если работа ветки уже на `main`. Логика проверки, а не согласования.
5. Второй заход того же дефекта, замеченный при заведении этого эпика: гард отклонил
   **сообщение коммита**, которое описывает проблему, потому что в нём цитируется команда.
   «Называние субъекта не есть действие» — у гарда уже есть carve-out'ы ровно этого класса
   (`grep -rn publish`, `cat vercel.json`, `pnpm --filter .../telegram add`), и это ещё один
   его случай. Стоит закрыть заодно: судить только первый сегмент команды, а не весь текст
   `-m`/`-F`.

## Объём — карта файлов

- `.claude/hooks/live-effects-guard.sh` — carve-out.
- `test/hooks/run.sh` — кейсы.
- `.claude/commands/finish-branch.md` — если формулировка шага должна измениться.

## Вне объёма

- `neonctl projects delete` и `databases delete`. Они остаются запрещёнными безусловно.
- Удаление удалённой git-ветки (`git push origin --delete`). Отдельный случай, остаётся в
  `permissions.deny`.
- Автоматическая уборка осиротевших веток Neon. Отдельная задача.

## Критерии приёмки

- [ ] КОГДА удаляется ветка Neon вида `agent/<slug>`, для которой в `git worktree list` нет
      worktree и нет каталога слота, ТО команда проходит.
- [ ] КОГДА удаляется ветка Neon, для которой worktree ещё существует,
      ТО команда отклоняется — это живая работа соседа.
- [ ] КОГДА удаляется `main` или любая ветка не по шаблону `agent/<slug>`,
      ТО команда отклоняется.
- [ ] КОГДА удаляется проект или база (`projects delete`, `databases delete`),
      ТО команда отклоняется независимо от имени.
- [ ] КОГДА новый кейс прогоняется на коде до починки,
      ТО первый краснеет, а остальные три остаются зелёными — carve-out не стал байпасом.

## Верификация

```bash
bash test/hooks/run.sh
pnpm verify
```

## Границы

**Carve-out не должен становиться префиксом.** Проверять надо не только имя ветки, но и
отсутствие живого worktree — иначе достаточно назвать ветку `agent/что-угодно`, чтобы снести
чужую базу. Это тот же урок, что уже записан рядом про `pnpm install && ...`.

**Проверка по состоянию, а не по намерению.** Гард не может узнать, что его вызвал
`/finish-branch`. Единственный надёжный признак — что уборка уже произошла: worktree снят,
слот освобождён. На это и опираться.
