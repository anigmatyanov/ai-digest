# /epic-review

**Исполнитель никогда не оценивает собственную работу.** Детерминированные проверки делаешь ты, суждение делегируешь ревьюеру со свежим контекстом.

## 1. Механические проверки — делает родительская сессия

```bash
BR=agent/<slug>
git diff --name-only main...$BR        # сверь с "## Объём — карта файлов"
```

Всегда допустимо сверх карты: соседние `*.test.ts`, файл самого эпика, стабы найденной работы.

**Целостность контракта.** В диффе файла эпика допустимы только: `[ ]` → `[x]`, заполнение `## План реализации`, дописывание в конец `## Заметки`. Правка frontmatter или текста критериев — **критическая находка**.

Сравнивай с **merge-base**, а не с main — иначе то, что main сделал после ответвления, читается как откат, сделанный исполнителем:

```bash
git show "$(git merge-base main $BR):docs/epics/E-NNN-<slug>.md" > /tmp/base.md
git show "$BR:docs/epics/E-NNN-<slug>.md" | diff /tmp/base.md -
```

Собери список неотмеченных критериев и причин.

## 2. Верификация перепрогоняется в worktree

Не верь отчёту исполнителя. Зайди в `.claude/worktrees/<slug>` и прогони **каждую** команду из `## Верификация` сам. Для `touches_output` — `pnpm golden` и дифф выпуска; для `costs_llm` — `pnpm cost:report` и дельта к baseline; для `ui_visible` — скриншот с порта слота.

## 3. Суждение — свежему ревьюеру

Запусти агента `code-reviewer` (read-only, проходит хук без worktree). Вставь в промпт **дословно**: `## Цель`, `## Критерии приёмки`, `## Объём`, `## Границы`, затем `git diff --stat main...$BR` и полный дифф, если он меньше ~1500 строк, иначе список файлов и абсолютный путь worktree.

Проси по каждой находке: файл, строку, серьёзность (critical/warning/info) и конкретную починку.

**Ревьюеру напомни:** прежде чем назвать расхождение в эпик-файле нарушением, установить merge-base (см. выше). Эта ложная критическая находка выносится чаще любой другой.

## 4. Вердикт

Таблица: по каждому критерию — подтверждён / нет / чем доказан · карта файлов · целостность контракта · находки по серьёзности · дифф выпуска · дельта стоимости · ручные шаги. Затем **владелец** решает: принять → `/finish-branch`, доработать → флип `review → in-progress` и повторный диспатч, отбросить → снести ветку и worktree.

**Правило двух правок.** Дважды просили доработку по одной и той же проблеме — не просите третий раз. Выбрасывайте ветку и переформулируйте эпик: перезапуск дешевле уговоров.
