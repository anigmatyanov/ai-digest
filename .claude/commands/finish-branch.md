# /finish-branch

## Жёсткие правила — никогда не нарушать

- НИКОГДА `git push --force`.
- НИКОГДА `git reset --hard`.
- НИКОГДА `git branch -D`. Только `-d` (безопасное удаление).
- НИКОГДА не удаляй удалённую ветку.
- Если что-то выглядит неправильно — грязное дерево, push не прошёл, ветка не смержена — **STOP и доложи**. Не импровизируй в обход гейта.

## Шаги

**1. Pre-check.** Дерево чистое, ты на `main`, `git pull --ff-only`.

**2. Rebase-clean гейт.** Это то, что ловит конфликты, которые `--plan` предсказать не мог:

```bash
git merge-tree --write-tree main "$BR" >/dev/null 2>&1 || {
  echo "Ветка не мержится чисто на текущий main."
  echo "STOP. Верни её на ребейз — не ребейзи автоматически."
  exit 1
}
```

**3. Squash-merge и закрытие эпика одним коммитом.** Порядок нагружен смыслом: правка эпика попадает **в тот же** коммит, что и код, иначе история покажет фичу без закрытого контракта.

```bash
git merge --squash "$BR"
# в файле эпика: status: done, done: <YYYY-MM-DD>
git add docs/epics/E-NNN-<slug>.md
git commit -m "feat(E-NNN): <summary>"
git push origin main
```

**4. Уборка. Удаление ветки НЕ согласовывается с владельцем.**

`git branch -d` после squash-merge не сработает никогда: squash не оставляет ancestry, и git считает ветку несмерженной навсегда. Поэтому используется `-D`, а безопасность обеспечивает хук `git-branch-delete-guard.sh`, а не человек.

Хук проверяет ровно то, ради чего существовал прежний запрет: **каждый файл, который ветка изменила от merge-base, либо лежит на main с тем же содержимым, либо когда-то лежал** (main мог уехать вперёд поверх него). Если да — удаление проходит молча. Если нет — отказ с именами файлов, и это единственный случай, когда нужен человек.

Симметричный `git diff main <branch>` для этого не годится и был отвергнут: он показывает и то, что main получил ПОСЛЕ мержа, поэтому отставшая ветка неотличима от держащей работу. Измерено — два файла, которые main изменил после мержа, отчитывались как «работа, которая потеряется».

**Порядок нагружен смыслом, и имя ветки пишется буквально.** Neon-ветку удаляет
`live-effects-guard.sh`-разрешённая команда, но разрешение выдаётся не по имени, а по
состоянию: ветка вида `agent/<slug>`, которой уже нет в `git worktree list` и на которую не
держится слот. Поэтому уборка идёт именно в этом порядке — worktree, слот, потом Neon, — и
поэтому `"$BR"` здесь не годится. Хук не может раскрыть переменную вызывающей оболочки: с
`"$BR"` он не находит ни ветки, ни worktree и отказывает (а `git-branch-delete-guard.sh`,
наоборот, не находит локальной ветки с таким именем и просто отходит в сторону — то есть
переменная тихо снимает обе проверки). Подставь настоящий slug.

```bash
git branch -D "agent/<slug>"                          # хук решает сам
git worktree remove ".claude/worktrees/<slug>"
rm -rf ".claude/worktrees/.slots/<N>"                 # освободить слот
command -v neonctl >/dev/null && neonctl branches delete "agent/<slug>"
git worktree prune
```

Если Neon-ветку всё же отказались удалять — это сигнал, что уборка выше не доехала: worktree
остался зарегистрированным или слот не освобождён. Проверь `git worktree list` и
`.claude/worktrees/.slots/`, а не обходи гард.

**`git worktree remove` здесь уничтожает секрет, а не только директорию.** С 2026-08-29 в
`.claude/worktrees/<slug>/.env` лежит живая строка подключения к ветке Neon этого слота
(E-015), правами 600 и вне git. Измерено: `.env` попадает под `.gitignore`, а игнорируемый
файл `git worktree remove` **не** останавливает — команда выше проходит без `--force` и
удаляет `.env` вместе с директорией. Отсюда следствие: **оставленная директория worktree —
это оставленная лежать строка подключения.** Если `remove` отказал (агент оставил
неигнорируемые несохранённые файлы) — разберись с ними и повтори, а не бросай директорию.

Удалённая ветка (`git push origin --delete`) — отдельный случай: она остаётся в `permissions.deny`, потому что это действие наружу, и его отменить нельзя тем же способом.

**5. Отчёт.** Что смержено, какой эпик закрыт, какой слот освобождён, что осталось в очереди (`node scripts/epics.mjs --plan`).

**Деплой:** пуш в `main` не публикует выпуск. Пайплайн запускается по расписанию в GitHub Actions.
