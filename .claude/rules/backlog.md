# Backlog rules — слой исполнения

`docs/epics/` — очередь работы для агентов. Один файл = один эпик = одна свежая сессия = один squash-PR.

**Эпики никогда не переезжают между директориями.** Терминальный статус живёт во frontmatter (`status: done` + `done: YYYY-MM-DD`), а очередь показывает `node scripts/epics.mjs`. Это сознательное отличие от исходного проекта: там архивация через `git mv` породила 166 мёртвых ссылок и отдельный скрипт для их починки. Здесь ссылка на эпик не может протухнуть, потому что файл не двигается.

## Стейт-машина и матрица прав

```
draft → todo → in-progress → review → done
review → in-progress (доработка) | in-progress → todo (протухший claim) | любой → dropped
```

| Что                                                                                                          | Кто меняет                                      | Где коммитится           |
| ------------------------------------------------------------------------------------------------------------ | ----------------------------------------------- | ------------------------ |
| Создание эпика, `draft→todo`                                                                                 | владелец + `/epic-new`                          | main                     |
| `todo→in-progress`, `claimed_by`, `branch`                                                                   | родительская сессия (`/epic-next`), ДО диспатча | main                     |
| `## План реализации`, чекбоксы AC (только ставить), `## Заметки` (только дописывать), стабы найденной работы | **только** субагент-исполнитель                 | его ветка `agent/<slug>` |
| `in-progress→review`                                                                                         | родительская сессия, прочитав финальный отчёт   | main                     |
| `review→done` + `done:`                                                                                      | `/finish-branch`, внутри того же squash-коммита | main                     |
| `любой→dropped` + причина в Заметках                                                                         | только владелец                                 | main                     |
| **Текст** критериев, `## Объём`, `## Границы`, `## Верификация`, любое поле frontmatter                      | только владелец                                 | main                     |

### Жёсткие правила исполнителя

- **НИКОГДА не редактируй frontmatter.** Даже свой статус. Даже если он очевидно неверен.
- **НИКОГДА не редактируй, не удаляй и не переформулируй текст критериев приёмки.** Чекбокс ставится только при наличии доказательства. Ослабленный критерий — критическая находка на ревью.
- **`## Заметки` — append-only, и «append» значит в самый конец секции**, после всех существующих строк, включая те, что владелец добавил на main уже после старта твоей ветки. Вставка «в хронологическое место» — это правка чужого блока, и в диффе она невидима.
- **Правильная правка owner-only секции всё равно не твоя.** Если работа показала, что `## Объём`, `## Границы` или текст критерия неверны — положи **дословную замену** в `## Заметки` и в финальный отчёт. Владелец применит её на main. Быть правым не передаёт права.
- **Если инструкция родительской сессии противоречит одобренному `## План реализации`** — следуй инструкции, работу не делай, и доложи конфликт с дословной формулировкой того, что не применил. Инструкция позже по времени, план шире по полномочиям, примиряет владелец.
- **При конфликте мержа в эпик-файле** выровняй frontmatter по текущим значениям main тем же коммитом. Ветка никогда не везёт frontmatter в мерж.

### Ревьюеру: сначала merge-base, потом обвинение

Прежде чем назвать расхождение в эпик-файле нарушением, установи базу. `git diff main...<branch>` показывает и то, что main сделал **после** последнего мержа — это читается ровно как откат, сделанный исполнителем. Сравнивай с базой:

```bash
git show "$(git merge-base main <branch>):docs/epics/E-NNN-<slug>.md"
```

Отличие от merge-base — находка. Отличие от main при совпадении с merge-base — это main уехал вперёд, и находки нет.

## Rubric готовности (`--validate`)

`draft` переводится в `todo`, когда есть:

- одно предложение `## Цель` — наблюдаемый результат, не список работ;
- ≥1 критерий вида `- [ ] КОГДА …, ТО …` (наблюдаемый исход, **не** шаг реализации);
- ≥1 команда в fenced-блоке под `## Верификация`;
- ≥1 путь под `## Объём`;
- `size ∈ {S, M}` — **L не бывает**, режется на эпики с `depends_on`;
- каждый `depends_on` существует;
- каждая `serialize`-метка есть в реестре ниже.

Предупреждения (не блокируют): пустой или вне-словарный `area`; `autonomy: auto` на эпике, чей `## Объём` трогает `packages/telegram`, `packages/db/prisma` или `packages/llm/src/prompts` — эти области обязаны быть минимум `plan-gated`; `costs_llm: true` без `pnpm cost:report` в `## Верификация`; `touches_output: true` вместе с `autonomy: auto`.

**Команда в `## Верификация`, чей вердикт зависит от `DATABASE_URL`, обязана пинить цель инлайн.** Внутри worktree это Neon-ветка слота, а не та БД, против которой шли остальные команды, и `.env` подставит её молча.

## Правило найденной работы

Работа вне карты файлов **филится, а не делается**. Исполнитель создаёт стаб из `_template.md` по пути `docs/epics/E-<родитель><буква>-<slug>.md` со `status: draft` и `discovered_from: E-<родитель>`, ссылается на него в `## Заметки` и в отчёте, и остаётся на своём эпике.

Буквенный суффикс — ровно одна буква, и он берётся от **числового** родителя: стаб, найденный в `E-012c`, становится `E-012d`, а не `E-012ca`. Свободная буква считается по `docs/epics/` целиком, включая `dropped` — снятый id это постоянная занятость, а не переиспользуемый слот.

**Гранулярность идёт за картой.** Если `## Объём` сузил файл до названных секций, правило действует на уровне секций. Исключение — изменение, которое является прямым следствием самого диффа: оно делается и перечисляется в `## Заметки`.

## Serialize-реестр

Если карта файлов эпика трогает файл из реестра — соответствующая метка обязана быть в `serialize:`. Два эпика с общей меткой никогда не выполняются одновременно: метка удерживается и в `in-progress`, и в `review`, до самого мержа.

| Метка               | Что запирает                                                                     | Почему это hotspot                                                                                                                           |
| ------------------- | -------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `prisma-schema`     | `packages/db/prisma/schema.prisma`, `packages/db/prisma/migrations/**`           | Две параллельные миграции дают расходящуюся историю и дрейф shadow-БД                                                                        |
| `pipeline-contract` | `packages/core/src/pipeline/pipeline.ts`, `packages/core/src/pipeline/stage.ts`  | Список стадий и сигнатура `Stage` — их правят все                                                                                            |
| `core-types`        | `packages/core/src/types.ts`, `packages/core/src/schema/*.ts`                    | `RawItem`/`Candidate`/`Card`/`Edition` читают все стадии                                                                                     |
| `core-errors`       | `packages/core/src/errors.ts`                                                    | Классы, на которые ветвится раннер                                                                                                           |
| `profile-schema`    | `profiles/schema.ts`                                                             | Смена схемы мгновенно инвалидирует все профили                                                                                               |
| `profiles`          | `profiles/*.ts`                                                                  | Правка чужого профиля почти всегда значит, что эпик разросся                                                                                 |
| `prompts`           | `packages/llm/src/prompts/**`                                                    | Дело не в текстовом конфликте, а в **измеримости**: golden-дифф двух одновременно изменённых промптов невозможно приписать конкретному эпику |
| `llm-costs`         | `packages/llm/src/cost.ts`, `packages/llm/src/pricing.ts`, `costs/baseline.json` | Два параллельных обновления дают baseline, которого не было ни в одном прогоне                                                               |
| `env-schema`        | `packages/core/src/env.ts`, `.env.example`                                       | Каждая новая переменная приходит сюда                                                                                                        |
| `web-shell`         | `apps/web/src/app/layout.tsx`, `apps/web/src/app/globals.css`                    | Оболочка и токены темы                                                                                                                       |
| `workflows`         | `.github/workflows/**`                                                           | Cron продукта и CI; YAML мержится плохо                                                                                                      |
| `toolchain`         | `package.json`, `tsconfig*.json`, `eslint.config.js`, `pnpm-workspace.yaml`      | Корневой манифест и конфиги правят все, а конфликт в них ломает `verify` для всех живых веток                                                |

**Реестра коннекторов в этом списке нет намеренно.** `packages/connectors/src/index.ts` генерируется командой `pnpm gen:connectors` из содержимого директории, поэтому два агента, добавляющие по коннектору, не правят один файл руками. Устранённый хотспот лучше запертого: метка **сериализует** работу, кодогенерация — **распараллеливает** её.

**Тот же вопрос задавай каждому новому кандидату в реестр:** его можно сгенерировать? Если да — генерируй, а не запирай.

Конфликты на файлах _вне_ реестра `--plan` предсказать не может: реальный список файлов не стартовавшего эпика ещё не существует. Их ловит rebase-clean гейт в `/finish-branch`.

## Правила нарезки

- Эпик не пересекает границу `packages/core ↔ apps/web`, кроме случая, когда веб-часть — чистый потребитель уже смерженного типа.
- **Один коннектор = один эпик.** Не «добавить RSS, HN и GitHub» — это три эпика, запускаемых одновременно.
- **Эпик с `touches_output: true` в батче ровно один.** Иначе на ревью невозможно сказать, чей дифф улучшил выпуск, а чей испортил. Это не про конфликты в git, это про измеримость.
- **Эпик с `costs_llm: true` тоже одиночка** — он держит `llm-costs`.
- Миграция с бэкфиллом — `paired`, субагенту не делегируется.
- Практический потолок — **4–6 одновременных worktree**. Ограничитель не git, а ревью: владелец физически смотрит выпуск-диффы последовательно.

## Словарь `area`

Ровно одна на эпик; группировка для владельца, на планирование не влияет.

`connectors` · `pipeline` · `llm` · `web` · `profiles` · `infra` (CI, cron, деплой, миграции) · `tooling` (скрипты, бэклог, харнессы — не продукт).

## Уровни автономии

- `auto` — `/epic-next` берёт и диспатчит без вопросов.
- `plan-gated` — read-only `Plan`-агент пишет `## План реализации`, владелец одобряет до кода. Для регрессионно-опасного и для всего, что меняет наблюдаемый выпуск.
- `paired` — субагенту не делегируется, работается интерактивно. **Обязательно для:** миграции с бэкфиллом; любого изменения в `packages/telegram`, касающегося публикации; смены модели или структуры промпта стадии `compose`.

**Пункт «Спросить заранее», в который работа предсказуемо упрётся, несовместим с `autonomy: auto`.** У auto-агента некого спрашивать. Либо предреши в `## Объём`/`## Вне объёма`, либо ставь `plan-gated`. Если auto-агент всё же упёрся: возьми самый консервативный вариант внутри карты, зафиксируй в `## Заметки` и выбранный, и отвергнутый — но не расширяй карту и не останавливайся.

**Развилка, которую дорого отменить** (форма схемы БД, контракт выпуска, формат профиля), и по которой есть ≥2 жизнеспособных подхода с реальным трейд-оффом — повод один раз позвать скилл `llm-council` внутри `plan-gated`-стопа. Отдельного гейта и поля для этого нет: это инструмент, а не ступень процесса.

## Удаление ветки — автономное действие

Агент удаляет отработавшую ветку сам и **не спрашивает владельца**. Согласование здесь было бы ритуалом: владелец одобрял бы каждое удаление одинаково, а решение принимается по проверяемому признаку, а не по суждению.

Признак проверяет `.claude/hooks/git-branch-delete-guard.sh`: каждый файл, изменённый веткой относительно merge-base, обязан лежать на main с тем же содержимым либо когда-то лежать. Ветка, не удовлетворяющая этому, не удаляется — и вот тогда это вопрос к владельцу.

Следствие для `/finish-branch`: `git branch -d` после squash-merge не срабатывает никогда (squash не оставляет ancestry), поэтому используется `-D`, и это не нарушение, а нормальный путь. Запрет остаётся только на удаление **удалённой** ветки: это действие наружу.

## Протухшие claim'ы

Эпик `in-progress`, чьей ветки уже нет, показывает `--stale`. Сбрасывает только родительская сессия и только после подтверждения владельцем. **Субагент не сбрасывает claim'ы никогда.**

## Свежесть контракта

Эпик — контракт, написанный на дату. Очередь глубокая, соседи мержатся мимо, и **ничто не проверяет, что его посылка ещё верна**: `--validate` смотрит форму, не содержание. Перед claim'ом эпика, созданного раньше последнего мержа, трогающего его предмет:

```bash
git log --oneline --since=<created> -- <файлы из ## Объём>
```

Если посылка уехала — владелец правит owner-only секции на main **до** коммита claim'а.

## Rules retrospective

Каждый агент — исполнитель, ревьюер, родительская сессия — закрывает финальный отчёт оценкой **самих правил**. Три строки, всегда в этом порядке:

- **Сработало:** конкретное правило или гейт, который здесь реально предотвратил ошибку. Назови его. «Всё было хорошо» — не ответ.
- **Мешало или молчало:** правило, оказавшееся неверным, устаревшим, непропорционально дорогим — или **отсутствующее** там, где дефект всё равно проскочил. Если честно нечего сказать — напиши «нет».
- **Предложение:** конкретная правка (файл + формулировка) или «изменений нет».

**Предложение дублируется в `## Заметки` эпика, а не только в отчёт.** Отчёт — это чат: он живёт до компакции контекста родительской сессии. `## Заметки` переживают её и едут с эпиком.

Агент **никогда не применяет правки правил сам** — владелец курирует. Церемониальная ретроспектива («правила отличные») и выдуманное ради заполнения предложение считаются дефектами отчёта наравне с неотмеченным критерием.

## Пропорциональная церемония

Опечатки, однострочники, правки доков — префикс `quick:` в `description` субагента, без эпика. Активных эпиков (todo + in-progress + review) — не больше ~15; скрипт предупреждает.
